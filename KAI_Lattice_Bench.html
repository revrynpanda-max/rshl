KAI Lattice — Throughput, Efficiency & Accuracy

Live benchmark of the RSHL core (RSHL_USB/rshl-core-v3.mjs, mirrored from src/core/sparse_vec.rs). Measured on Node v22, single-threaded, May 14 2026.
Bottom line: The lattice is working. Code is healthy — the Rust core compiles clean (verified earlier, 0 warnings), and every JS/HTML file checked is valid. Throughput is solid (~1.14 billion dot-ops/sec on one CPU thread). VSA recall is functional — 78–100% recall@K with a positive signal margin at every bundle size. The one real issue: the encoder runs far sparser than its documented 12% spec — see Efficiency below.

The Lattice & Its 4 Sub-Lattices

Every thought is a 16,384-dimensional sparse ternary vector (each dimension is -1, 0, or +1). The lattice is partitioned into 4 sub-lattices of 4,096 dims each — the Region enum in src/core/regions.rs:

Left · 0
4,096 dims — logic, structure, gain-driven
Right · 1
4,096 dims — associative, salience + temporal
Bridge · 2
4,096 dims — cross-hemisphere binding
Global · 3
4,096 dims — unified awareness

Dots above are illustrative — lit dots show roughly the measured active-dimension density of a typical cell (~0.6%).

Efficiency — Sparsity (the one real issue)

The core advertises 12% density (~1,966 active dims). Measured reality is much sparser — the encoder places only 24 dims per token and the 12% sparsification floor never engages for normal-length text:

Text lengthActive dimsDensity
1 word240.15%
3 words (typical short cell)72–94~0.57%typical
8 words1921.17%
20 words4802.93%
50–120 words624 (plateau)3.81%ceiling
Documented target1,96612.0%never reached

Is this broken? Not exactly — sparser vectors are faster and recall still works (below). But it has a real cost: superposition capacity. The fix is a core encoding change (raise per-token dims, or make the sparsification floor adaptive) and it would re-encode the whole lattice — an architect decision, not a silent edit. Flagging, not changing.
